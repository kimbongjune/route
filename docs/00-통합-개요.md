# 한국형 내비게이션 + routedb 통합 기획·설계

2026-10-10 · 봉준

## 개요

한국 정부 공개데이터만으로 동작하는 **자동차 내비게이션 서비스**와, 그 경로 탐색을 담당하는 **도로망 특화 DBMS(routedb, 임시명)**를 한 세트로 만든다. 둘 다 Rust로 짜고, 내비게이션이 routedb를 쓰는 첫 번째 실제 클라이언트가 된다.

- **최종 목표 1 — 내비게이션**: 웹(모바일 브라우저 포함)에서 실시간 GPS 추적, 최적 경로 계산, 턴바이턴 안내, 안전 정보(카메라·사고다발·스쿨존·과속방지턱) 알림, 자체 지도(2D → 2.5D)를 제공한다.
- **최종 목표 2 — routedb**: 도로망 데이터를 DB처럼 넣고·고치고·조회하면서 경로 계산은 전용 엔진(OSRM급)만큼 빠른 DBMS. 1차는 내비에 임베디드로 붙고, 이후 자체 프로토콜·JDBC를 갖춘 독립 서버가 된다.
- **한 세트로 묶는 이유**: 내비에 필요한 그래프 저장·CCH·실시간 가중치·경로 계산 코드가 routedb 엔진과 **같은 코드**다. 따로 두 번 만들 이유가 없고, 직접 만든 DB를 실제 서비스로 검증할 수 있다.
- **이 문서는 두 프로젝트의 원본 기획서를 하나로 통합한 최신본이다.** 기존 [내비게이션 기획문서](https://claude.ai/artifact/TD9p8HkdbazRwDD6W3e9gb)와 [경로 특화 DBMS 기획](https://claude.ai/artifact/DymVwtwE2EDbBEoqNWVjd4)의 결정 사항을 모두 반영했다.

## 두 프로젝트의 관계와 경계

기준은 하나다: **"그래프를 들고 경로를 계산하는 일"은 routedb, "데이터를 모아 오고 사용자에게 보여주는 일"은 내비.**

| 일 | 담당 | 비고 |
|---|---|---|
| 표준노드링크 파싱 → 그래프 구성 → CCH 빌드 | routedb (`importer-knl`, `core`) | 기존 내비 설계의 `preprocess`가 여기로 옮겨옴 |
| 그래프·인덱스 저장 | routedb 저장 계층 | 지리적으로 가까운 교차로를 같은 페이지에 배치한 바이너리, mmap |
| 링크 속성(제한속도, 스쿨존, 카메라·방지턱 태그, 차량 제한, 유료 여부) | routedb | "넣고 고치고 조회"가 DB의 본업 |
| 실시간 가중치 반영(CCH customize) | routedb | `UPDATE` 형태로 받음 |
| 경로 계산 + ETA + 턴바이턴 안내문 | routedb `route()` → Route 타입 | |
| ITS 소통정보·돌발정보 폴링 | 내비 `collector` | 받아서 routedb에 UPDATE |
| HTTP API, 지오코딩 프록시, 사고다발 폴리곤 교차(1차), 프론트 정적 서빙 | 내비 `api` | 라우팅 로직 없는 얇은 계층(BFF) |
| 배경지도·건물 타일 | 내비 (PostGIS + GeoServer) | routedb와 무관 |
| 지도 렌더링, GPS 추적, 근접 알림, 이탈 감지 | 내비 `web` (브라우저) | |
| 자체 프로토콜, Rust 클라이언트, JDBC | routedb (2차, 별도 트랙) | 내비 1차에는 불필요 |

**연결은 임베디드 먼저, 서버 모드는 나중에.** 1차에는 `routedb-core` 크레이트를 내비 `api`가 같은 프로세스 안에서 직접 호출한다(SQLite처럼). 프로토콜·드라이버를 먼저 만들면 내비가 멈추기 때문이다. 엔진이 안정되면 routedb에 프로토콜 서버를 얹고, 내비는 직접 링크를 `routedb-client` 호출로 바꾸기만 한다.

즉 **DB 코드를 쓰는 건 지금, DB처럼 접속해서 쓰는 건 나중**이다.

## 전체 구성도

> 경로는 routedb가, 수집과 표출은 내비가 맡는다 (원본 데이터 3종 → 서버 3그룹 → 브라우저)

```
 ┌───────────────────────┐   ┌───────────────────────┐   ┌───────────────────────┐
 │ 표준노드링크·안전 POI │   │ 실시간 소통·돌발정보  │   │ 도로명주소 전자지도   │
 │ ITS·공공데이터포털 파일│   │ 수 분 간격 Open API   │   │ 배경지도·건물 원본    │
 └───────────┬───────────┘   └───────────┬───────────┘   └───────────┬───────────┘
             ▼                           ▼                           ▼
 ┌─ routedb (Rust 크레이트) ┐ ┌─ nav 서버 (Rust·axum) ─┐ ┌─ 지도서버 (Docker) ───┐
 │ ┌─────────────────────┐ │ │ ┌────────────────────┐ │ │ ┌───────────────────┐ │
 │ │ importer-knl        │ │ │ │ collector          │ │ │ │ PostGIS           │ │
 │ │ 파싱·속성 적재·CCH  │◀┼─┼─│ 폴링→routedb UPDATE│ │ │ │ 배경·건물 레이어  │ │
 │ └─────────┬───────────┘ │ │ └────────────────────┘ │ │ └─────────┬─────────┘ │
 │           ▼             │ │                        │ │           ▼           │
 │ ┌─────────────────────┐ │ │ ┌────────────────────┐ │ │ ┌───────────────────┐ │
 │ │ routedb-core  ★     │ │ │ │ api                │ │ │ │ GeoServer + GWC   │ │
 │ │ 저장 계층·CCH·가중치│◀┼─┼─│ route() 임베디드   │ │ │ │ 벡터 타일(MVT)    │ │
 │ │ route()→경로·안내문 │ │ │ │ JSON·지오코딩·정적 │ │ │ │ 사전 생성 캐시    │ │
 │ └─────────────────────┘ │ │ └─────────┬──────────┘ │ │ └─────────┬─────────┘ │
 └─────────────────────────┘ └───────────┼────────────┘ └───────────┼───────────┘
                                          │ 경로 JSON                │ 벡터 타일
                                          ▼                          ▼
 ┌─────────────────────────────────────────────────────────────────────────────────┐
 │ 브라우저 — nav/web (MapLibre GL JS)                                             │
 │ 경로 표시 · GPS 추적 · 근접 알림 · 이탈 시 재요청 · 2D → 2.5D                   │
 └─────────────────────────────────────────────────────────────────────────────────┘
```

세 가지 흐름으로 읽으면 된다.

- **배치(하루~월 1회)**: 표준노드링크·안전 POI 파일 → `importer-knl` → `routedb-core` 저장 계층 + CCH 인덱스. 도로명주소 전자지도 → PostGIS → GeoServer/GeoWebCache 타일 사전 생성.
- **상시(수 분 간격)**: `collector`가 소통정보·돌발정보를 폴링해 routedb에 UPDATE → CCH customize로 가중치만 갱신.
- **요청마다**: 브라우저가 `api`에 출발·도착을 보내면 `api`가 같은 프로세스 안의 `routedb-core`에 `route()`를 호출해 경로·ETA·안내문을 받고, 사고다발 교차를 붙여 JSON으로 응답. 지도 타일은 브라우저가 GeoServer에서 직접 받는다.

외부에 남는 실시간 의존은 **ITS·국토부 Open API**(데이터 수집)와 **브이월드 검색 API**(지오코딩, 추후 자체화) 두 가지뿐이다.

## 공통 원칙과 핵심 결정

| 주제 | 결정 | 근거 |
|---|---|---|
| 데이터 원칙 | **OSM 미사용**, 한국 정부·공공기관 공개데이터만 사용 | 국가가 관리하는 신뢰도, 전국 균일 커버 |
| 도로망 | 표준노드링크(국가교통정보센터) | 이미 노드/링크 그래프 구조, 실시간 소통정보와 링크 ID 동일 |
| 실시간 교통 | 국가교통정보센터 단일 소스 | 지자체(TOPIS·경기) 피드는 링크 체계가 달라 매칭 작업 필요, 국가 센터가 통합 창구 |
| 경로 알고리즘 | CCH(Customizable Contraction Hierarchies, `cch` 크레이트) | 구조 build와 가중치 customize 분리 — 실시간 반영의 전제 |
| 경로 엔진 위치 | routedb로 분리, 1차는 임베디드 | 같은 코드를 두 번 만들지 않음, 내비 일정과 DB 제품화를 분리 |
| 언어 | Rust (routedb·내비 서버 모두) | GC 없는 저지연, 대용량 그래프의 메모리 배치 제어 |
| 지도 표출 | **자체 지도서버**: 도로명주소 전자지도 → PostGIS → GeoServer 벡터 타일 + GeoWebCache 사전 생성 | 외부 실시간 의존 제거, 건물 두 겹 문제 원천 제거, 스타일 자유 |
| 지도 엔진 | MapLibre GL JS | 기울기·회전·건물 돌출·터치 제스처 내장 → 2D에서 2.5D로 엔진 교체 없이 확장. 키·사용료 없음 |
| 지오코딩 | 1차 브이월드 검색 API → 추후 적재된 도로명주소 DB로 자체화 | 유일하게 남는 외부 의존 |
| 배포 | Docker compose, 무상태 서버 복제로 확장 | 전처리는 배치(재실행), 서빙은 읽기 전용이라 복제 쉬움 |
| 범위 | 일반 승용차 내비 | 차폭·차장 정밀 라우팅, 대중교통, 블랙아이스 예측 등은 제외(사유는 내비 기획 문서) |

## 구현 단계 요약

routedb 엔진을 먼저 세우고, 그 위에 내비를 연결한 뒤, 지도·프론트·배포로 1차를 마무리한다. 상세 단계와 완료 기준은 [5. 구현 순서](05-구현-순서.md).

1. **준비·기초 (0~1단계)** — 인증키 신청, 데이터 다운로드, Rust 기초, 워크스페이스 뼈대
2. **routedb 엔진 (2~7단계)** — 임포터 → 저장 계층 → 다익스트라(M1) → CCH(M2) → 회전 제한·속성 → Route·안내문
3. **내비 서버 (8~9단계)** — 임베디드 API(M3) → 실시간 수집·반영
4. **지도·프론트·배포 (10~13단계)** — 지도 적재·타일 → 스타일 → 프론트 2D → 도커 (M4, 내비 1차 완성)
5. **2차 (14~17단계)** — 2.5D, 관리 페이지, 대안경로·최소요금, 자체 지오코더 (M5)
6. **routedb 독립 (18단계, 별도 트랙)** — 프로토콜 서버·JDBC, 내비를 클라이언트로 전환 (M6)

내비 1차까지 약 17~25주, 회사·학업과 병행하면 **6~8개월**이 현실적이다. 지도 작업(10~11단계)은 routedb와 독립이라 엔진 작업 중 막힐 때 병행할 수 있다.
