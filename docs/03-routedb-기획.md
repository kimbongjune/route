# routedb — 기획

도로망과 경로 탐색에 특화된 DBMS를 Rust로 직접 만든다(임시명 routedb). 어떻게 만드는지는 [routedb — 설계](04-routedb-설계.md)에 있다.

## 개요

데이터를 DB처럼 자유롭게 넣고 고치고 조회하면서, 경로 계산은 전용 경로 엔진 수준으로 빠른 것이 목표다. 범용 DBMS로는 MySQL이나 PostgreSQL을 이길 수 없다. 대신 도로망이라는 좁은 영역에 집중해 그 영역에서는 기존 DB보다 확실히 나은 것을 만든다.

- 경로 탐색을 기본 함수로 제공한다: `route(출발지, 도착지)`
- 실시간 가중치 변경을 빠르게 반영하면서 조회 속도를 유지한다
- 1차는 Rust 크레이트로 임베디드 사용, 이후 자체 프로토콜과 전용 JDBC 드라이버(`jdbc:routedb://`)를 갖춘 독립 서버
- 내비게이션 프로젝트의 경로 탐색 백엔드로 먼저 쓴다

## 배경과 문제

기존 선택지는 데이터 관리가 편하면 경로 계산이 느리고, 경로 계산이 빠르면 데이터 관리가 불편하다.

| 방식 | 데이터 관리 | 경로 계산 | 한계 |
|---|---|---|---|
| MySQL 등 일반 DB | 자유롭다 | 매우 느리다 | 재귀 쿼리로 억지로 탐색하거나 앱 메모리로 꺼내 계산 |
| PostgreSQL + pgRouting | 자유롭다 | 느리다 | 쿼리마다 그래프를 메모리로 불러와 계산, 대규모 도로망에서 한계 |
| OSRM·Valhalla 등 경로 엔진 | 불편하다 | 빠르다 | 미리 빌드해 읽기 전용으로 쓰는 구조라 수정·다른 데이터와의 조합이 어렵다 |
| **routedb (목표)** | 자유롭다 | 빠르다 | 만들어야 한다 |

## 핵심 컨셉

특화 대상은 특정 나라가 아니라 **도로망이라는 데이터 형태**다. 교차로(노드)와 도로 구간(링크), 거리·제한속도·회전 제한 같은 속성은 어느 나라 도로든 구조가 같다.

**범용 엔진 + 임포터**

- 핵심 엔진: 그래프 저장, 경로 탐색, 사전 계산 인덱스, 실시간 가중치 업데이트. 나라와 무관한 범용 부분
- 임포터: 포맷별로 데이터를 변환해 넣는 플러그인. 나라별로 달라지는 곳은 여기뿐이다. 첫 임포터는 한국 표준노드링크(내비가 OSM을 쓰지 않으므로 OSM 임포터는 인터페이스만 열어둔다)

**한국 확장 (차별점)** — "한국 데이터로 쓰기 가장 편한 경로 DB". 우선순위는 내비가 필요로 하는 순서를 따른다.

1. 표준노드링크 기본 지원(회전정보·통과제한 포함)
2. 국가 ITS 실시간 교통정보 연동(링크 ID 그대로 가중치 UPDATE)
3. 어린이보호구역 속도 제한(이후 시간제), 요일·시간대별 버스전용차로
4. 도로명·지번 주소를 좌표로 바꾸는 주소 검색

**활용 범위** — 가중치가 있는 연결망이면 같은 엔진을 쓸 수 있다. 자동차 도로로 시작하되 엔진은 범용으로 짠다. 보행자·자전거 경로, 물류 배송 동선, 지하철 환승, 건물 실내 길찾기, 게임 맵 등으로 넓힐 수 있다.

## 주요 기능과 쿼리 예시

SQL 전체를 구현하지 않는다. 경로 관련 핵심 쿼리 몇 가지를 제대로 지원하고, 나머지 노력은 저장 구조와 인덱스에 쏟는다. 1차(임베디드)는 SQL 파싱 없이 같은 기능을 Rust 함수로 제공하고, SQL 부분집합은 서버 모드에서 붙인다.

```sql
-- 최소 시간 경로 (1차: core.route(...))
SELECT route(출발지, 도착지, mode => 'fastest');

-- 실시간 교통 반영 (1차: core.update_weights(...))
UPDATE 도로구간 SET 통행시간 = 240 WHERE id = 1234;

-- 현재 위치에서 차로 15분 안에 갈 수 있는 영역 (서버 모드 이후)
SELECT reachable_area(현재위치, within => '15 min');

-- 도로 기준 가장 가까운 주유소 5곳 (서버 모드 이후)
SELECT * FROM 주유소 ORDER BY road_distance(현재위치, 위치) LIMIT 5;
```

핵심 과제는 UPDATE다. 사전 계산 인덱스는 가중치가 바뀌면 재계산이 필요하다. 구조와 가중치를 분리하는 CCH로 이 문제를 푼다.

## 자체 프로토콜과 JDBC 드라이버 (서버 모드)

메인 통신은 자체 프로토콜과 전용 JDBC 드라이버로 간다. PostgreSQL 프로토콜을 빌려 쓰면 드라이버 개발은 줄지만 `jdbc:postgresql://`로 접속하게 되어 이 DB의 정체성이 사라지고, 경로 결과를 텍스트나 JSON으로 뭉개서 보내야 한다.

```java
Connection conn = DriverManager.getConnection(
    "jdbc:routedb://localhost:7400/korea", "bongjun", "pw");
ResultSet rs = conn.createStatement()
    .executeQuery("SELECT route('서울역', '판교역', mode => 'fastest')");
rs.next();
Route route = rs.getObject(1, Route.class);   // 전용 타입으로 바로 받기
route.getDurationSec();
route.getPath();                              // 좌표 리스트
route.getTurnByTurn();                        // "300m 앞 우회전" 같은 안내
```

- 경로 타입을 바이너리로 효율적으로 주고받는다(전국 단위 경로는 좌표가 수천 개)
- 탐색 진행 스트리밍, "교통이 바뀌면 이 경로를 다시 알려줘" 같은 구독형 쿼리를 프로토콜 차원에서 설계할 수 있다
- DBeaver 같은 범용 툴 연동이 필요해지면 PostgreSQL 호환 모드를 보조 포트로 나중에 추가(`pgwire` 크레이트)

## 내비게이션과의 관계

- 내비의 경로 탐색 코드를 서비스 안에 묻어두지 않고 이 DB의 엔진으로 분리한다. 내비는 첫 클라이언트가 되고, 직접 만든 DB를 실제 서비스로 검증한다.
- **임베디드 먼저**: 프로토콜·JDBC를 먼저 만들면 내비가 멈춘다. 1차는 `routedb-core`를 내비 `api`가 같은 프로세스에서 직접 호출한다.
- **역할**: 그래프 저장·CCH·실시간 가중치·`route()`·Route 타입(안내문 포함)·링크 속성은 routedb. 실시간 API 폴링은 내비 `collector`가 받아 UPDATE로 밀어넣는다. 지도 타일은 routedb와 무관.

## 단계별 범위

| 단계 | 범위 | 내비 의존 |
|---|---|---|
| 1차 — 임베디드 엔진 | 표준노드링크 임포터, 저장 계층, 다익스트라/A*(검증용), CCH, 회전 제한·링크 속성, Route 타입·안내문, 가중치 UPDATE | 내비 1차에 필수 |
| 2차 — 서버 모드 | 바이너리 프로토콜, 프로토콜 서버, Rust 클라이언트, JDBC 드라이버, SQL 부분집합 | 내비 완성 후 별도 트랙 |
| 이후 | `reachable_area()`, `road_distance()`, 구독형 쿼리, 주소 검색, 다른 포맷 임포터, PostgreSQL 호환 포트 | — |
