# routedb 기획

도로망과 경로 탐색에 특화한 DBMS를 Rust로 직접 만든다. 이름은 아직 정하지 않았으며 임시로 routedb라 한다. 어떻게 만드는지는 [routedb 설계](04-routedb-설계.md)에 있다.

## 개요

데이터를 DB처럼 자유롭게 다루면서 경로 계산은 전용 경로 엔진 수준으로 빠른 것이 목표이다. 범용 DBMS로는 MySQL이나 PostgreSQL을 이길 수 없으므로 도로망이라는 좁은 영역에 집중해 그 영역에서는 기존 DB보다 확실히 나은 것을 만든다. 경로 탐색을 기본 함수 `route(출발지, 도착지)`로 제공하고, 실시간 가중치 변경을 빠르게 반영하면서 조회 속도를 유지하며, 1차는 Rust 크레이트로 임베디드 사용하고 이후 전용 프로토콜과 JDBC 드라이버 `jdbc:routedb://`를 갖춘 독립 서버로 만든다. 내비게이션의 경로 탐색 백엔드로 먼저 사용한다.

## 배경

기존 선택지는 데이터 관리가 편하면 경로 계산이 느리고 경로 계산이 빠르면 데이터 관리가 불편하다.

| 방식 | 데이터 관리 | 경로 계산 | 한계 |
|---|---|---|---|
| MySQL 등 일반 DB | 자유롭다 | 매우 느리다 | 재귀 쿼리로 탐색하거나 앱 메모리로 꺼내 계산한다 |
| PostgreSQL + pgRouting | 자유롭다 | 느리다 | 쿼리마다 그래프를 메모리로 적재해 계산하며 대규모 도로망에서 한계가 있다 |
| OSRM, Valhalla 등 경로 엔진 | 불편하다 | 빠르다 | 미리 빌드해 읽기 전용으로 사용하는 구조라 수정과 다른 데이터와의 조합이 어렵다 |
| routedb(목표) | 자유롭다 | 빠르다 | 만들어야 한다 |

## 기본 구상

특화 대상은 특정 나라가 아니라 도로망이라는 데이터 형태이다. 교차로와 도로 구간, 거리·제한속도·회전 제한 같은 속성은 어느 나라 도로든 구조가 같다. 범용 엔진과 임포터로 나누어 엔진은 그래프 저장, 경로 탐색, 사전 계산 인덱스, 실시간 가중치 업데이트 같은 나라와 무관한 부분을 담당하고, 임포터는 포맷별로 데이터를 변환해 적재하는 플러그인으로 나라별로 달라지는 부분을 담당한다. 첫 임포터는 한국 표준노드링크이며 내비가 OSM을 사용하지 않으므로 OSM 임포터는 인터페이스만 둔다.

한국 확장이 차별점이며 한국 데이터로 사용하기 가장 편한 경로 DB를 목표로 한다. 우선순위는 내비가 필요로 하는 순서로 표준노드링크 기본 지원(회전정보와 통과제한 포함), 국가 ITS 실시간 교통정보 연동(링크 ID 그대로 가중치 UPDATE), 어린이보호구역 속도 제한과 이후 시간제 및 요일·시간대별 버스전용차로, 도로명·지번 주소를 좌표로 변환하는 주소 검색 순이다.

가중치가 있는 연결망이면 같은 엔진을 사용할 수 있으므로 자동차 도로로 시작하되 엔진은 범용으로 구현하며 보행자·자전거, 물류 배송 동선, 지하철 환승, 건물 실내 길찾기, 게임 맵으로 확장할 수 있다.

## 기능과 쿼리 예시

SQL 전체를 구현하지 않고 경로 관련 쿼리 몇 가지를 제대로 지원하며 나머지 노력은 저장 구조와 인덱스에 쓴다. 1차 임베디드는 SQL 파싱 없이 같은 기능을 Rust 함수로 제공하고 SQL 부분집합은 서버 모드에서 추가한다.

```sql
-- 최소 시간 경로. 1차는 core.route(...)
SELECT route(출발지, 도착지, mode => 'fastest');

-- 실시간 교통 반영. 1차는 core.update_weights(...)
UPDATE 도로구간 SET 통행시간 = 240 WHERE id = 1234;

-- 현재 위치에서 차로 15분 안에 갈 수 있는 영역. 서버 모드 이후
SELECT reachable_area(현재위치, within => '15 min');

-- 도로 기준 가장 가까운 주유소 5곳. 서버 모드 이후
SELECT * FROM 주유소 ORDER BY road_distance(현재위치, 위치) LIMIT 5;
```

가장 어려운 문제는 UPDATE이다. 사전 계산 인덱스는 가중치가 바뀌면 재계산이 필요하므로 구조와 가중치를 분리하는 CCH로 해결한다.

## 전용 프로토콜과 JDBC 드라이버(서버 모드)

메인 통신은 전용 프로토콜과 전용 JDBC 드라이버로 한다. PostgreSQL 프로토콜을 빌리면 드라이버 개발은 줄지만 `jdbc:postgresql://`로 접속하게 되어 이 DB의 정체성이 사라지고 경로 결과를 텍스트나 JSON으로 변환해 보내야 하기 때문이다.

```java
Connection conn = DriverManager.getConnection(
    "jdbc:routedb://localhost:7400/korea", "bongjun", "pw");
ResultSet rs = conn.createStatement()
    .executeQuery("SELECT route('서울역', '판교역', mode => 'fastest')");
rs.next();
Route route = rs.getObject(1, Route.class);   // 전용 타입으로 바로 받는다
route.getDurationSec();
route.getPath();                              // 좌표 리스트
route.getTurnByTurn();                        // "300m 앞 우회전" 같은 안내
```

전국 단위 경로는 좌표가 수천 개이므로 경로 타입을 바이너리로 효율적으로 주고받으며, 탐색 진행 스트리밍과 "교통이 바뀌면 이 경로를 다시 알려줘" 같은 구독형 쿼리를 프로토콜 차원에서 설계할 수 있다. DBeaver 같은 범용 툴 연동이 필요해지면 PostgreSQL 호환 모드를 `pgwire` 크레이트로 보조 포트에 이후 추가한다.

## 내비게이션과의 관계

내비의 경로 탐색 코드를 서비스 안에 두지 않고 이 DB의 엔진으로 분리하며 내비는 첫 클라이언트로서 직접 만든 DB를 실제 서비스로 검증한다. 프로토콜과 JDBC를 먼저 만들면 내비 개발이 멈추므로 임베디드를 먼저 하여 1차는 내비 `api`가 `routedb-core`를 같은 프로세스에서 직접 호출한다. 그래프 저장, CCH, 실시간 가중치, `route()`, 안내문을 포함한 Route 타입, 링크 속성은 routedb가 담당하고 실시간 API 폴링은 내비 `collector`가 받아 UPDATE로 전달하며 지도 타일은 routedb와 무관하다.

## 단계별 범위

| 단계 | 범위 | 내비 의존 |
|---|---|---|
| 1차 임베디드 엔진 | 표준노드링크 임포터, 저장 계층, 검증용 다익스트라와 A*, CCH, 회전 제한과 링크 속성, Route 타입과 안내문, 가중치 UPDATE | 내비 1차에 필수 |
| 2차 서버 모드 | 바이너리 프로토콜, 프로토콜 서버, Rust 클라이언트, JDBC 드라이버, SQL 부분집합 | 내비 완성 후 별도 트랙 |
| 이후 | `reachable_area()`, `road_distance()`, 구독형 쿼리, 주소 검색, 다른 포맷 임포터, PostgreSQL 호환 포트 | |

## 열린 질문

- [ ] DB 이름을 정한다. 후보는 샛길, 길목, 마루이며 임시는 routedb이다.
- [x] 실시간 가중치 방식은 CCH(`cch` 크레이트)로 확정하였다.
- [x] 쿼리 인터페이스는 1차 함수 호출 API, SQL 부분집합은 서버 모드에서 하기로 하였다.
- [x] 한국 확장 우선순위는 표준노드링크, ITS, 스쿨존, 주소 검색 순으로 정하였다.
- [ ] 전용 프로토콜의 메시지 종류와 바이너리 포맷 상세는 서버 모드 단계에서 정한다.
- [ ] 사고다발 폴리곤 교차를 언제 routedb 공간 함수로 이관할지 정한다.
- [ ] 주소 검색을 routedb 한국 확장에 넣을지 내비 쪽 PostGIS에 둘지 정한다.
